**Tags**: #testing #quality #workflow #bestpractice

**Solution**:
Implemented a zero-tolerance policy for test failures:
1. Run tests immediately after implementation
2. Fix ALL failing tests before considering feature complete
3. Never commit code with failing tests
4. Track down root causes, not just symptoms

In this session, we fixed:
- Button variant error (component API mismatch)
- FAQ category loading logic (incorrect filtering)
- Function argument order (scope, faq, attrs)
- Missing admin authorization hook
- Security hole in router configuration

**Rationale**:
- **Quality**: Failing tests indicate broken functionality
- **Regression Prevention**: Unfixed errors compound over time
- **Code Health**: Each skipped error makes the next one easier to ignore
- **Trust**: Test suite must be trusted to catch real issues
- **Documentation**: Tests document expected behavior - failures are lies

**Why it matters**:
This principle applies to ALL features, not just FAQ:
- Security tests MUST pass (auth, scope isolation)
- Edge case tests MUST pass (empty states, validation)
- Integration tests MUST pass (LiveView interactions)

The test suite went from:
- **Before**: 276 tests, unknown failures in FAQ area
- **After**: 333 tests (+17 FAQ tests), all passing

## Category: Security

### Insight: Admin Authorization Requires Dedicated on_mount Hook

**File**: `lib/homesite_web/user_auth.ex:251-264`
**Tags**: #security #auth #liveview #authorization

**Problem**:
The `:require_admin` live_session was only checking for authenticated users, not admin role. Regular users could access admin-only routes like `/faqs/new` and `/faqs/:id/edit`.

**Solution**:
```elixir
def on_mount(:require_admin, _params, session, socket) do
  socket = mount_current_scope(socket, session)

  if socket.assigns.current_scope && Homesite.Accounts.Scope.admin?(socket.assigns.current_scope) do
    {:cont, socket}
  else
    socket =
      socket
      |> Phoenix.LiveView.put_flash(:error, "You must be an administrator to access this page.")
      |> Phoenix.LiveView.redirect(to: ~p"/")

    {:halt, socket}
  end
end
```

Then add to router:
```elixir
live_session :require_admin,
  on_mount: [
    {HomesiteWeb.UserAuth, :require_authenticated},
    {HomesiteWeb.UserAuth, :require_admin},  # NEW
    {HomesiteWeb.SetLocaleHook, :default}
  ] do
```

**Rationale**:
- LiveView `on_mount` hooks run before every mount
- Multiple hooks can be chained for layered security
- `:require_authenticated` checks auth, `:require_admin` checks role
- Hooks should fail closed (redirect on error)

**Why it matters**:
This pattern should be used for ALL admin-only routes:
- Admin dashboard
- User management
- Invitation management
- FAQ management
- Any future admin features

Security tests verify this works:
```elixir
test "regular users cannot access FAQ creation form", %{conn: conn} do
  user = user_fixture()
  conn = log_in_user(conn, user)

  assert {:error, {:redirect, %{to: _}}} = live(conn, ~p"/faqs/new")
end
```

## Category: Bugs

### Insight: DaisyUI Button Component Has Limited Variant Support

**File**: `lib/homesite_web/live/faq_live/index.ex:21-26`
**Tags**: #bug #ui #daisyui #component

**Problem**:
Used `<.button variant="ghost">` based on common UI patterns, but got error:
```
KeyError at GET /faqs
key "ghost" not found in: %{nil => "btn-primary btn-soft", "primary" => "btn-primary"}
```

**Solution**:
Use `<.link>` with DaisyUI classes instead of `<.button>` for non-primary buttons:
```heex
<!-- Wrong -->
<.button variant="ghost" navigate={~p"/faqs?category=user"}>
  {gettext("User FAQs")}
</.button>

<!-- Right -->
<.link navigate={~p"/faqs?category=user"} class="btn">
  {gettext("User FAQs")}
</.link>
```

**Rationale**:
- The `<.button>` component in `core_components.ex` only supports `variant="primary"` or `variant=nil`
- DaisyUI has many button variants (ghost, outline, link, etc.) via CSS classes
- Use `<.link class="btn btn-ghost">` for DaisyUI variants
- Reserve `<.button>` for primary CTAs only

**Why it matters**:
This is a common gotcha when working with the Phoenix `<.button>` component:
- Check `lib/homesite_web/components/core_components.ex` for supported variants
- Don't assume component supports all DaisyUI variants
- When in doubt, use `<.link class="btn btn-{variant}">` for DaisyUI control

## Category: Bugs

### Insight: Context Function Argument Order Must Match Definition

**File**: `lib/homesite_web/live/faq_live/form.ex:141`
**Tags**: #bug #elixir #context #pattern

**Problem**:
FunctionClauseError when validating FAQ form:
```elixir
# Wrong - piped faq is first argument
socket.assigns.faq
|> Faqs.change_faq(socket.assigns.current_scope, faq_params)

# Function expects: change_faq(scope, faq, attrs)
```

**Solution**:
```elixir
# Right - scope is first, faq is second
Faqs.change_faq(socket.assigns.current_scope, socket.assigns.faq, faq_params)
```

**Rationale**:
- Scope-first is the pattern for ALL context functions in this app
- Pipe operator changes natural argument flow
- Elixir won't match `%Faq{}` against `%Scope{}` parameter

**Why it matters**:
This applies to ALL context functions:
```elixir
# Correct pattern throughout app
Content.get_post!(scope, id)
Content.create_post(scope, attrs)
Content.update_post(scope, post, attrs)
Content.change_post(scope, post, attrs)

Faqs.get_faq!(scope, id)
Faqs.create_faq(scope, attrs)
Faqs.update_faq(scope, faq, attrs)
Faqs.change_faq(scope, faq, attrs)
```

Avoid pipe-first when context functions need scope:
```elixir
# Don't do this
post |> Content.update_post(scope, attrs)

# Do this
Content.update_post(scope, post, attrs)
```

## Category: Architecture

### Insight: FAQ Category Loading Requires Separate Function Calls

**File**: `lib/homesite_web/live/faq_live/index.ex:120-134`
**Tags**: #liveview #context #filtering #architecture

**Problem**:
Initial implementation tried to filter `list_admin_faqs` by category:
```elixir
# Wrong - list_admin_faqs only returns admin FAQs
Faqs.list_admin_faqs(scope, locale)
|> Enum.filter(&(&1.category == category))
```

When category="user", this returned empty list because admin FAQs are filtered out by the database query.

**Solution**:
Use case statement with separate function calls:
```elixir
defp load_faqs(socket, category) do
  if socket.assigns.is_admin do
    case category do
      "admin" -> Faqs.list_admin_faqs(socket.assigns.current_scope, socket.assigns.locale)
      "user" -> Faqs.list_user_faqs(socket.assigns.locale)
      _ -> []
    end
  else
    if category == "user" do
      Faqs.list_user_faqs(socket.assigns.locale)
    else
      []
    end
  end
end
```

**Rationale**:
- `list_admin_faqs` applies WHERE clause for category="admin"
- `list_user_faqs` applies WHERE clause for category="user" AND is_active=true
- Can't filter results that are already filtered by database
- Need to call different functions for different categories

**Why it matters**:
This pattern shows importance of understanding what queries return:
- Don't assume context functions return ALL records
- Database filtering happens before Elixir filtering
- Read context function implementations to understand constraints
- Test category switching to verify correct data loading
