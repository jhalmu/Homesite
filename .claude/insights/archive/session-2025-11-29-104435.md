## Category: Database

### Insight: PostgreSQL Trigram Search with Dual Matching Strategy

**File**: `lib/homesite/content.ex:724-764`, `priv/repo/migrations/20251129081009_add_search_index_to_posts.exs`
**Tags**: #postgresql #search #performance #fts

**Problem**:
Needed full-text search for blog posts that handles both exact matches and fuzzy/typo-tolerant matching. Traditional ILIKE is slow on large datasets, and pg_trgm alone might miss exact substring matches.

**Solution**:
Combined PostgreSQL trigram similarity with ILIKE fallback:

```elixir
# Migration - Enable extension and create GIN indexes
execute "CREATE EXTENSION IF NOT EXISTS pg_trgm"
execute "CREATE INDEX posts_title_trgm_idx ON posts USING gin (title gin_trgm_ops)"
execute "CREATE INDEX posts_body_trgm_idx ON posts USING gin (body gin_trgm_ops)"

# Query - Dual matching strategy
from(p in Post,
  where: not is_nil(p.published_at) and p.is_public == true,
  where:
    fragment("similarity(?, ?) > 0.1", p.title, ^query) or
    fragment("similarity(?, ?) > 0.1", p.body, ^query) or
    fragment("? ILIKE ?", p.title, ^"%#{query}%") or
    fragment("? ILIKE ?", p.body, ^"%#{query}%"),
  order_by: [
    desc: fragment(
      "greatest(similarity(?, ?), similarity(?, ?))",
      p.title, ^query, p.body, ^query
    )
  ]
)
```

**Rationale**:
- **Trigram similarity (0.1 threshold)**: Catches typos, partial matches, fuzzy queries
- **ILIKE fallback**: Ensures exact substring matches are never missed
- **GIN indexes**: Fast for both similarity and ILIKE operations
- **Ordered by similarity**: Most relevant results first
- **Low threshold (0.1)**: Cast wider net, let ILIKE catch exact matches

**Why it matters**:
This pattern works for any text search scenario. The dual strategy ensures:
- Users find what they're looking for even with typos
- Exact matches always appear (ILIKE guarantees this)
- Performance stays fast with proper indexes
- Results are ranked by relevance

Applied to both public search (`search_posts/2`) and user-scoped search (`search_user_posts/3`).

### Insight: Empty Query String Handling Prevents Database Overload

**File**: `lib/homesite/content.ex:726-728`, `test/homesite/content_search_test.exs:164-168`
**Tags**: #security #validation #performance #dos

**Problem**:
Search functions could be called with empty or whitespace-only queries, potentially returning all posts in the database. This is both a performance issue and potential DoS vector.

**Solution**:
```elixir
def search_posts(query, opts \\ []) when is_binary(query) do
  # Return empty list for empty or whitespace-only queries
  case String.trim(query) do
    "" -> []
    trimmed_query -> # ... perform search with trimmed_query
  end
end
```

Also handle negative limits:
```elixir
limit = Keyword.get(opts, :limit, 20)
limit = max(limit, 0)  # Ensure non-negative
```

**Rationale**:
- **Security**: Prevents returning entire database on empty query
- **Performance**: Avoids expensive queries for meaningless input
- **UX**: Empty search = no results is intuitive behavior
- **Database safety**: PostgreSQL raises error on negative LIMIT

**Why it matters**:
This is a common vulnerability in search implementations. Always validate query parameters before hitting the database:
1. Check for empty/whitespace queries
2. Validate numeric parameters (limits, offsets)
3. Return early with sensible defaults

Edge case tests caught this - we initially allowed empty queries through, which returned ALL posts in tests.

### Insight: Database Constraint Violations Should Be Tested with assert_raise

**File**: `test/homesite/social_test.exs:113-127`, `test/homesite/social_test.exs:209-224`
**Tags**: #testing #ecto #database #constraints

**Problem**:
When testing that very long strings fail database constraints (VARCHAR(255)), we initially used `assert {:error, _} = result` expecting a changeset error. Instead, Ecto raises a `Postgrex.Error` exception.

**Solution**:
```elixir
test "handles very long URLs", %{post: post} do
  # URLs longer than 255 chars will fail due to database constraint
  long_url = "https://example.com/" <> String.duplicate("a", 300)

  attrs = %{
    platform: "twitter",
    shared_url: long_url,
    post_id: post.id
  }

  # Should raise database error (URL column is VARCHAR(255))
  assert_raise Postgrex.Error, fn ->
    Social.log_share(attrs)
  end
end
```

**Rationale**:
- **Changeset validations** return `{:error, changeset}`
- **Database constraints** raise exceptions
- Length constraints at DB level bypass Ecto changesets
- Test assertions must match actual error handling

**Why it matters**:
Understand the difference between validation layers:
1. **Schema validation**: `validates_length(:field, max: 255)` → Returns changeset error
2. **Database constraint**: `VARCHAR(255)` → Raises exception
3. **Foreign key constraint**: `references(:table)` → Can return changeset error if using `foreign_key_constraint/3`

When testing database constraints, use `assert_raise`. When testing schema validations, use `assert {:error, changeset}`.

**File**: `lib/homesite/social.ex`, `lib/homesite/social/share_log.ex`
**Tags**: #context #analytics #separation-of-concerns

**Problem**:
Social sharing could have been added directly to the Content context, but this limits future analytics capabilities and mixes concerns.

**Solution**:
Created dedicated `Homesite.Social` context:

```elixir
# Core function - log share events
def log_share(attrs \\ %{}) do
  %ShareLog{}
  |> ShareLog.changeset(attrs)
  |> Repo.insert()
end

# Analytics functions
def get_post_share_stats(post_id)  # Per-post stats
def get_all_share_stats()          # Site-wide rankings
def list_recent_shares(limit)       # Activity feed
```

Database schema:
```elixir
schema "share_logs" do
  field :platform, :string
  field :shared_url, :string
  field :ip_address, :string
  field :user_agent, :string

  belongs_to :post, Homesite.Content.Post
  belongs_to :user, Homesite.Accounts.User

  timestamps(type: :utc_datetime, updated_at: false)
end
```

**Rationale**:
- **Separation**: Social features separate from core Content
- **Analytics**: Share logs foundation for future dashboard
- **Flexibility**: Can track shares of non-post content later
- **Privacy**: Optional IP/user_agent tracking
- **Cascade**: Deletes with posts, nullifies on user delete

**Why it matters**:
When adding features, consider:
1. Is this a separate concern? → New context
2. Will this need analytics? → Log events with rich metadata
3. What are the relationships? → Proper foreign keys and cascades
4. What's the privacy impact? → Optional sensitive fields

The Social context is ready for:

**File**: `lib/homesite_web/components/social_components.ex`
**Tags**: #components #responsive #social #ux

**Problem**:
Different social platforms have different share URL formats and requirements. Need responsive UI that works on mobile and desktop.

**Solution**:
Component-based approach with platform-specific URL builders:

```elixir
def social_share_buttons(assigns) do
  ~H"""
  <div class={"#{@class} flex flex-wrap gap-2"}>
    <.share_button platform="bluesky" url={@url} title={@title} />
    <.share_button platform="mastodon" url={@url} title={@title} />
    <.share_button platform="twitter" url={@url} title={@title} />
    <!-- ... -->
  </div>
  """
end

defp share_button(assigns) do
  ~H"""
  <a href={@share_url} target="_blank" rel="noopener noreferrer"
     class="btn btn-sm btn-outline gap-2">
    <.icon name={@icon_name} class="h-4 w-4" />
    <span class="hidden sm:inline">{@label}</span>
  </a>
  """
end

# Platform-specific URL construction
defp build_share_url("bluesky", url, title) do
  text = URI.encode_www_form("#{title} #{url}")
  "https://bsky.app/intent/compose?text=#{text}"
end

defp build_share_url("mastodon", url, title) do
  text = URI.encode_www_form("#{title} #{url}")
  "https://mastodonshare.com/?text=#{text}"  # Universal Mastodon share
end
```

**Rationale**:
- **Responsive**: `hidden sm:inline` shows labels only on larger screens
- **Security**: `noopener noreferrer` prevents window.opener attacks
- **Flexibility**: Easy to add new platforms (just add URL builder)
- **Encoding**: Proper URL encoding prevents injection
- **Decentralized social**: Mastodon uses mastodonshare.com for instance selection

**Why it matters**:
Social share button patterns apply to any content type:
- Blog posts
- Images/galleries
- User profiles
- Custom pages

Key principles:
1. Mobile-first (icons only on small screens)
2. Security (proper link attributes)
3. Proper encoding (all text/URLs)

### Insight: Scope Isolation Must Be Tested for All New Features

**File**: `test/homesite_web/security_test.exs:338-468`
**Tags**: #security #testing #scope #isolation

**Problem**:
New features (search, social sharing) must enforce the same scope isolation as existing features. Without tests, security holes can slip through.

**Solution**:
Added dedicated security test sections:

```elixir
describe "Search Security: Scope isolation in search results" do
  test "user search only returns their own posts" do
    # Create posts for two users with same keyword
    {:ok, post_a} = Content.create_post(scope_a, %{title: "Secret Post"})
    {:ok, _post_b} = Content.create_post(scope_b, %{title: "Secret Post"})

    # User A searches
    results_a = Content.search_user_posts(scope_a, "Secret")

    # Should only see their own post
    assert length(results_a) == 1
    assert hd(results_a).id == post_a.id
    assert Enum.all?(results_a, fn p -> p.user_id == user_a.id end)
  end

  test "search does not leak data between scopes" do
    # Create posts with sensitive data
    {:ok, _post_a} = Content.create_post(scope_a, %{title: "API Key: sk-1234"})
    {:ok, _post_b} = Content.create_post(scope_b, %{title: "API Key: sk-5678"})

    # User A searches
    results_a = Content.search_user_posts(scope_a, "API Key")

    # Should only see their own API key
    assert hd(results_a).title =~ "sk-1234"
    refute hd(results_a).title =~ "sk-5678"
  end
end
```

**Rationale**:
- **Mandatory**: Every scoped feature needs security tests
- **Data leaks**: Search is particularly prone to cross-user leaks
- **Regression**: Security tests prevent future bugs
- **Realistic**: Test with sensitive data (API keys, passwords)

**Why it matters**:
Security testing checklist for new features:
1. ✅ Users cannot access other users' data
2. ✅ SQL injection is prevented
3. ✅ XSS payloads are handled safely
4. ✅ Scope checks exist in context functions
5. ✅ Public vs private data is correctly filtered

This session added security tests for:
- Search scope isolation (5 tests)

- Total: 12 new security tests

Security is not optional - every feature must have security tests.
